# EasyInput shared gateway

The Worker and SQLite Durable Object provide authenticated board WSS, shared presence, a single persistent voice timeline, stable browser identities, transient realtime microphone forwarding, and a separate Xiaozhi proxy for browser Mandarin transcription. The static Studio PWA is deployed separately using Workers Static Assets with `studio.wrangler.jsonc`.

Released on 2026-10-30 (Asia/Shanghai): Studio **0.4.11** and the gateway are deployed, and firmware **0.4.24** is flashed. Public HTML, main JavaScript, CSS, manifest, Service Worker and Workbox resources match the local build; device-image hashes and post-flash startup checks passed. All 180 tests across 20 files, the webpage build, cloud type checking and ESP-IDF build passed. Deployment IDs, detailed evidence and Git delivery status are recorded in [testing progress](../docs/TESTING_PROGRESS.md). Live Xiaozhi binding/transcription, physical sound and network behavior still require manual verification.

`PUBLIC_DEVICE_ID` identifies the one default room. Any browser on an allowed Studio origin can join this room without a token; every visitor shares its messages and board status. The board still requires `PAIRING_SECRET`, saved once to its NVS. Keep this secret unchanged when deploying to preserve already provisioned boards. Non-default rooms require the token for browsers too.

## Deploy

From `cloudflare/`, set the long random `PAIRING_SECRET` with Wrangler secrets when initially provisioning, then use:

```bash
npm run typecheck
npm run deploy
```

From the repository root, run `npm test` and `npm run build`, then publish the static app:

```bash
cd cloudflare
npx wrangler deploy -c studio.wrangler.jsonc
```

The configured custom domains are `easy.leige.online` for the gateway and `studio.leige.online` for the page. `ALLOWED_ORIGINS` must include the page origin. Deploy the gateway before Studio and firmware so `/asr` and the new shared 60-second upload limit are available to the new browser. The existing domain route covers both `/ws` and `/asr`; no additional route or secret is introduced. Ordinary deployment retains the Durable Object namespace and stored messages; keep its binding, migration history and `PAIRING_SECRET` unchanged. No new storage product or paid TTS provider is required by this implementation.

- A fresh board status is required for online presence. A WSS connection or cached status alone is insufficient. The freshness window is 8 seconds; direct board Wi-Fi takes priority over a browser Bluetooth gateway.
- Firmware 0.4.24 gates the shared cloud WSS lifecycle on valid station IP and system time, recreates the client after IP loss/network-generation change, and adds WebSocket Ping/Pong, TCP keepalive and close/TLS/socket/HTTP/memory diagnostics. Control frames and realtime audio alternate while queued together; realtime audio older than 250 ms is dropped. Actual disconnection causes and long-term stability still require post-deployment observation; board Xiaozhi sessions use a separate connection.
- Browser identities persist in localStorage but no longer map to physical S1–S4/S8 slots.
- Original voice is 8 kHz mono G.711 mu-law. Browser dialect recording and `begin/chunk/commit` uploads allow up to 60 seconds; historical Flash outbox recordings retain their original 20-second limit. Since firmware 0.4.23, S5 streams acknowledged chunks to durable cloud storage, saves one message only after finish, and does not require a browser to be open. The browser split UI and client method are removed in Studio 0.4.11; historical split references and the server's legacy handler remain compatible.
- Studio offers a separate 60-second Mandarin recording path through `/asr`, using browser WebCodecs raw Opus and an independent persisted Xiaozhi web identity. First use may require official-platform binding; the physical board identity and S6/S7 sessions are not reused. The browser waits for readiness before opening its microphone, and stopping retains up to 20 seconds for final recognition. Only recognized user text is committed, with the browser sender identity and `read:true`; it does not enter board voice indices, unread counts or audio exports. Empty results produce an error. Stable ownership/completion receipts deduplicate retries; one room processes one browser transcription at a time. Original microphone audio is not saved as a voice message.
- The room retains at most 5000 committed voice and text messages. At capacity it removes the oldest eligible message (a board recording or an already-read message); unread browser messages are protected. If all 5000 are unread browser messages, new uploads are rejected. Complete board playback marks the message read; the explicit board `readAll` operation also marks unread timeline items read while preserving history and audio. Hold S1 for three seconds, release, then hold S2 for three seconds to confirm; browser playback does not mark board messages read.
- Stored metadata and audio survive reconnects and Worker upgrades. Legacy clips and chunk layouts remain readable. New S5 append transactions persist bounded immutable chunks and exact offsets before ACK; finish publishes metadata atomically without assembling a full clip. An independent 90-second no-data alarm preserves an abandoned received prefix as interrupted. New S5 capture uses a bounded RAM ring; the eight-slot Flash outbox remains for older recordings only. See `../docs/PROTOCOL.md` for cancellation tombstones, split references and incremental cleanup.
- A protected `POST /admin/clear` endpoint requires the `CLEAR_TOKEN` secret. It permanently removes timeline metadata, audio chunks, and incomplete uploads for the default room; connected browsers receive the removal immediately.
- Manual browser text input and the `/tts` endpoint are removed. S7 continuously sends speech to Xiaozhi and adds recognized user text to the shared timeline, potentially as several messages; it does not play Xiaozhi TTS. Existing text and pending deliveries are retained. S6 dialogue does not add text or audio to this timeline. Board prompt audio is generated at build time.
- The webpage directly opens/closes capture through the shared `realtime.set` toggle; `settings.realtime_enabled` is a capture command. Opening requires a fresh direct board Wi-Fi route and idle board resources. Any board work, including S1–S8 playback, transfer, timing, dialogue, recording and related prompts, immediately cancels requested/active listening. Busy work rejects a later enable request; completing work or reconnecting never automatically restores it. Start timeout (8 seconds), disconnect, or stale Wi-Fi presence also clears the toggle and active state. Board realtime audio uses 20 ms PCM16 binary frames, is forwarded only to browsers while active, and is never persisted.
- Presence updates still send the unique online-browser count. S5/S6/S7 start on release; during start, connection or activity, any S1–S8 or encoder-button press stops the voice function and is consumed through release. S5 saves the tail, S6 stops microphone/playback, and S7 drains final recognition and display receipts. S5 long-press cancellation is removed. Rotation changes volume. Sixty seconds without detected voice while listening or a 60-minute cap ends normally; S6 thinking/playback pauses the silence clock, but not the total cap. Outside board voice sessions, S8 starts an idle stopwatch on release. Every complete minute immediately plays a one-second tone, mixed into concurrent playback. While timing, any physical key DOWN stops the stopwatch and a parallel voice session, consuming the press through release. A stopping press cannot start S8 or another function; countdown and stopwatch remain independent.
- Normal playback volume changes immediately and is coalesced into `audio/volume` NVS once 750 ms have elapsed since the last adjustment and microphone/speaker are idle. Startup restores the last successful save. Immediate power loss, continued audio activity or a failed save may therefore restore the previous saved volume.
- All five indicators use red at 1% brightness. Slow blink is 0.5 seconds on and 1.5 seconds off; timer flash is 0.5 seconds on and 0.5 seconds off. LED 1 blinks during reception/download, otherwise stays on for unread voice. LED 2 prioritizes a one-minute alarm blink over timer flash over a steady configured alarm; timers continue beneath the display priority. LED 3 is steady during S5 capture or S6/S7 sessions, otherwise blinks for pending voice/text. LED 4 blinks only during active webpage realtime capture. LED 5 is steady when Wi-Fi is connected, blinks while connecting/retrying, and is off when disconnected without an active connection attempt. An alarm plays its due announcement, then loops the existing short melody for 60 seconds of actual music playback. Busy audio defers the sound without extending its one-minute indicator window; any physical key DOWN stops active alarm music and consumes the press.
- Existing board measurement and ledger data, pending uploads and browser CSV exports remain available. The independent NVS queues retain up to 64 pending measurements and 64 pending ledger entries from earlier firmware, synchronized through Wi-Fi or the selected Bluetooth gateway. The room persists stable IDs and deduplicates retries; browsers export all synchronized records through paginated `health.list` / `ledger.list`, independent of voice-history pruning. Presence and snapshots expose `ledgerPending` alongside `healthPending`, or null when the board is offline. Record synchronization resumes after a Xiaozhi session ends.

The older `agent/` LAN process is not required for either direct Wi-Fi or the browser Bluetooth gateway. Wi-Fi provisioning and firmware flashing remain on local USB/encrypted BLE. See `../docs/VOICE_CHAT.md` and `../docs/PROTOCOL.md` for usage and the wire contract.

Board ping acknowledgements include the actual `wifi` / `ble` transport for local network announcements. Board commit receipts (`delivered:<id>`) remain after audio/history eviction to avoid posting the same persisted recording twice after a lost acknowledgement. These small receipts contain no audio or Wi-Fi credentials. Firmware 0.2.1 also supports phone SoftAP provisioning and a durable eight-clip outbox; see [VOICE_CHAT.md](../docs/VOICE_CHAT.md).

## 5000-message history

Released with Studio 0.4.3 and board firmware 0.4.13. Deploy the gateway before the webpage and firmware so existing messages can be migrated while older clients remain compatible.

Browser snapshots include only the newest 50 messages plus room `total`, `unread`, and an older-history cursor `next`. `list` pages use a `(created, id)` cursor and a fixed `through` bound for full exports; new arrivals cannot move that bound. Studio 0.4.11 scrolls to the latest message at the bottom on refresh and preserves a visible anchor while loading older history. Its “最早未读 · Alt+U” action loads enough history to find the whole room's oldest unread board-bound voice message, without marking it read; the count is labeled “开发板 N 条未读” / “开发板全部已读”. The webpage offers chronological full-history playback and ZIP downloads of at most 100 WAV files or approximately 64 MiB per package, with a larger single message alone in its package. Each next package is explicitly downloaded from the page; no unbounded audio cache or automatic fifty-file download burst is used.

Board `index` requests with `count:8` return bounded batches (under the existing 2048-byte command ceiling). A persisted revision lets unchanged synchronization finish in one request and requires a restart if the index changes between pages. The legacy single-item request remains supported for older firmware. The new firmware allocates its 5000-entry metadata index in PSRAM, about 440 KB; the offline outbox remains eight recordings.

If all 5000 messages are full 60-second browser original-voice clips, they contain 2,400,000,000 raw audio bytes (2.4 GB), before SQLite, metadata and receipts; PCM WAV exports total approximately 4.8 GB and are split across packages. S5 recordings can be longer, while browser Mandarin transcription stores text only. The maximum count is an application retention policy, not a guarantee of remaining account storage or request quota. Verify the deployed Cloudflare plan, current platform limits and actual database usage before filling it. Ordinary deploys must keep the same namespace and binding to preserve data.


S7 uses `text.put` with `require_display:true`; `text.ack` confirms cloud persistence and includes `displayed:boolean`. Only the board or its selected Bluetooth gateway may submit this operation. Browser Mandarin results use the server-owned ASR save path and browser sender identity; arbitrary browser `text.put` remains unavailable. A browser sends `text.displayed` with the message ID only after its mounted chat component commits board text to the DOM; the gateway persists that receipt, acknowledges the browser request and forwards a separate `text.displayed` notification without `req` to the board. A repeated retained `text.put` without a display receipt rebroadcasts the message with `added:false,display_required:true`, preserving message counts and allowing a browser that missed the initial delivery to display it. Legacy submissions without `require_display` keep their cloud-acknowledgement behavior. Mixed timeline pages preserve the 5000-message limit, while board voice indices and ZIP/playback skip text. Stable receipts deduplicate retries.

After S7 stops capture, recognition may drain for up to 20 seconds; once recognition terminates, a separate 12-second deadline bounds remaining display receipts. Success requires at least one result and a display receipt for every result in the session from at least one mounted webpage chat component. Cloud storage alone is insufficient; empty results, processing errors, partial display or an expired deadline produce failure. Unconfirmed text stays in the FIFO and retries after failure without a delayed success cue; it no longer blocks a new S7 session unless the queue is completely full. Only the persisted `stt/pending` head has a cross-reboot guarantee; additional queued text remains in RAM.

Firmware establishes the session boundary atomically when the engine accepts a new start. Older ACKs retire prior FIFO entries without adding to the new session's `acked_texts`. Success uses only the new session's `received_texts`, `acked_texts` and `session_queued_texts`; status `queued_texts` continues to report all pending text across sessions. `session_queued_texts` counts actual remaining FIFO entries for this session, so explicit cancellation can clear it without fabricating ACKs. Diagnostics distinguish `delivery.no_text`, `delivery.offline`, `delivery.display_timeout`, `delivery.engine_failed` and `delivered`, preserving the first existing engine error. Canceling the start prompt or rejecting an engine start skips final delivery-diagnosis writeback while retaining engine-start errors. Manual regression must cover retry after a failed round, old and new deliveries mixed together, duplicate old ACKs after a new message becomes inflight, and an empty new recognition while old messages are acknowledged. No new gateway operation or redeployment is required for this counting fix.

The retained `ledger.summary` protocol describes Beijing-calendar today/yesterday/day-before totals plus latest amount and a count of unknown dates; S6 no longer opens it. Existing ledger history is backfilled on first request and subsequent deduplicated writes update totals transactionally. S6 Xiaozhi dialogue connects directly through board Wi-Fi, pauses microphone capture during response playback, and resumes listening after playback finishes. Board S7 recognition also uses direct board Wi-Fi independently of this gateway. The separate browser `/asr` proxy introduced with Studio 0.4.11 forwards audio to Xiaozhi and persists recognized text only; it does not synthesize TTS or store S6 dialogue audio.
